# Checking this mock against a real Plone

This mock's job is to behave like the Plone REST API. When that is in doubt,
check it against one of these — not against what our own callers happen to
expect. Three bugs came from doing the latter: an action's destination read from
`@id` when Plone emits `url`, `delete` looked up in `object` when Plone puts it
in `object_buttons`, and action ids invented by reading Volto's consumer code
instead of a Plone response.

**plone.restapi's recorded responses** — real HTTP captured from a live Plone
and regenerated by upstream's own test suite:

    https://github.com/plone/plone.restapi/tree/main/src/plone/restapi/tests/http-examples

The ones relevant here are `actions_get`, `workflow_get`, `workflow_post_with_body`,
`sharing_folder_get`, `sharing_folder_post`, `workingcopy_get` and
`workingcopy_post`. Deliberately not vendored: fetch them when you need them, so
what you read is current rather than a copy that has quietly aged.

**A live Plone 6**, for anything anonymous can see:

    curl -H 'Accept: application/json' https://demo.plone.org/++api++/@actions

Two limits worth knowing before you trust either source:

- **`actions_get.resp` predates the serializer gaining `url`.** Its entries are
  `[icon, id, title]`; the live response is `[icon, id, title, url]`, and Volto
  reads `url`. Where they disagree, the live one is current. WHICH entries
  appear, and in which category, is still authoritative in the recording.
- **The recorded site has no `plone.app.iterate`**, so it records no
  `iterate_checkout` / `iterate_checkin`. Those ids here are inferred from what
  Volto gates its working-copy buttons on, not recorded — the one thing in this
  mock's actions that is not backed by a response.

`@sharing` and an authenticated `@workflow` return 403/401 anonymously, so those
shapes rest on the recordings rather than on a call you can make yourself.
